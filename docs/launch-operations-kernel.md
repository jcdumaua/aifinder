# Launch Operations Kernel

Status: local concrete live-capable nonproduction qualification entrypoint plus a separately routed, post-publication-authorization-bound `ADMIN_V1_OFFICIAL_RUNTIME_V1` executor candidate. Both lanes have been exercised only with synthetic/local dependencies; they have not read live credentials, opened the network, or been executed live.

## Purpose

Replace future use of the Delta-heavy qualification runtime with a compact, deterministic, local-first operations kernel. The retained Phase 34IA-34IZ state remains immutable and unresolved until a separately reviewed legacy-reconciliation phase.

## Design

The candidate has eleven boundaries plus one independently identified pre-import trust bootstrap:

1. `kernel.mjs` owns the eight-state lifecycle, authorization checks, bounded budgets, compact evidence, and the single recovery controller.
2. `manifest.mjs` owns deterministic candidate discovery, canonical identity generation, derived surface identities, source-policy validation, and static readiness.
3. `legacy-classifier.mjs` may only read the exact retained local artifacts and emits a sanitized categorical classification.
4. `cli.mjs` exposes only local verification, identity reporting, static readiness, and read-only legacy classification.
5. `legacy-freeze.json` records the immutable legacy identities, the non-current routing decision, and the approval boundaries.
6. `nonproduction-qualification-authorization.mjs` and its JSON Schema own the exact one-attempt, 24-hour-or-less authorization record and future independent-review approval digest.
7. `nonproduction-qualification-runner.mjs` contains the sole live-capable dispatcher, with exact and disjoint `--qualify-nonproduction` and `--run-admin-v1-official` modes. Both fail closed unless the separately verified supervisor supplies the matching exact in-memory trust handoff.
8. `nonproduction-qualification-credential-loader.mjs` is the sole credential-source reader. Only after supervisor trust and runner pre-effect authorization, it opens repository-root `.env.local`, parses without evaluation or expansion, and resolves the seven runtime categories from the eight-name allowlist. `GH_TOKEN` takes deterministic precedence over `GITHUB_TOKEN`; when neither GitHub alias is nonempty, the exact existing GitHub CLI source is read in memory. When `VERCEL_TOKEN` is empty or absent, the exact existing macOS Vercel CLI `auth.json` source is read in memory. The five remaining categories must come from `.env.local`. `nonproduction-qualification-adapters.mjs` validates that explicit resolved map and binds the fixed five-resource plan to the bridge.
9. `nonproduction-qualification-live-platform.mjs` owns the allowlisted Git, Vercel Preview/environment, synthetic `submitted_tools`, staging-verification, and exact-version Storage calls.
10. `nonproduction-qualification-checkpoint-store.mjs` is the sole durable journal/external-binding writer and enforces local CAS persistence in a run-specific Downloads directory.
11. `fresh-resource-plan-diagnostics.mjs` owns the closed provider/resource/request-step/failure enum register used only by `VERIFY_FRESH_RESOURCE_PLAN`. It emits no locator, URL, hostname, project reference, provider body, credential path, token, or secret.
12. `admin-v1-official-runtime.mjs` owns the fixed six-request qualification ledger, fixed twenty-request Official ledger, nine-name environment contract, twenty-one-route deferred set, one-session/no-retry/no-replay controls, explicit external-action budgets, adapter boundary, synthetic fixture/effect accounting, exact-version Storage cleanup, sanitized projection, and mode-`0700`/`0600` durable journal. Its separate JSON Schema binds an authorization-supplied published HEAD, equal local `origin/main` and bounded remote-main observations, the operation class, contract identities, route/support identities, and one-use execution namespace. No source byte contains the future publication commit.
13. `admin-v1-official-authorization.mjs` builds a future authorization only after independently observed HEAD, local `origin/main`, bounded remote main, exact reviewed policy identities, and temporary-commit parent all agree. It writes only canonical mode-`0600` secret-free records when a later authority invokes the writer; this candidate creates none.
14. `admin-v1-official-live-platform.mjs` owns the exact action-cost-to-transport map, Official credential buffers, operation allowlist, bounded result validation, current low-level Git/provider transport binding, and the direct call into the unchanged Official state machine. Tests substitute only its operation-level low-level transport.

Outside the candidate-manifest trust domain, `scripts/launch-operations-supervisor/nonproduction-qualification-supervisor.mjs` uses only Node platform primitives to validate the exact separately reviewed supervisor policy, raw authorization envelope, candidate manifest and member closure, support and semantic pins, runner path/hash, retained freeze, and repository assumptions. Local repository inspection uses the deny-network, deny-write, helper-denying Git sandbox; Official mode adds exactly one bounded credential-free remote-main `ls-remote` and requires it to equal authorization HEAD and local `origin/main`. The Official source policy contains only invariant repository/binding rules, never a future commit literal. The supervisor dynamically imports the exact runner only after every trust check passes, rejects an authorization-path byte change across that import interval, and passes the already validated canonical authorization bytes, parsed object, independently computed digest, and exact repository observation directly to the real concrete factory and runner. Its policy binds the independently reviewed supervisor and policy identities used by the future one-attempt authorization; candidate resealing cannot silently update that policy.

`activation-bridge.mjs` remains the only qualification bridge. It imports no legacy entrypoint, reads no environment or credential, starts no process, and opens no network connection. The concrete runner can connect only the reviewed concrete adapters after its complete pre-effect authorization closure passes.

The canonical manifest excludes only its own bytes to avoid a circular self-hash. Its `candidate_roots` define the complete inventory; the verifier discovers every regular file under those roots, applies deterministic classification, and rejects missing, extra, reordered, symlinked, non-0644, or byte-mismatched members.

## Lifecycle

Current lifecycle states are `READY`, `QUALIFYING`, `QUALIFIED`, `OFFICIAL_RUNTIME_AUTHORIZED`, `OFFICIAL_RUNTIME_RUNNING`, `COMPLETE`, `FAILED_RECOVERABLE`, and `FAILED_CLOSED`. Historical Delta states are evidence only and cannot be used as current kernel states.

Official runtime requires the separate exact `ADMIN_V1_OFFICIAL_RUNTIME_V1` authorization. Its first Official application request spends the token; a second session, retry, replay, deferred handler, browser path, or legacy fallback is denied. No lifecycle transition grants Production or public authority. `FAILED_CLOSED` and `COMPLETE` are terminal.

## Recovery

The single recovery controller loads an authoritative local state and first validates its complete allowlisted shape. Every durable checkpoint carries a canonical identity over the exact static journal plus lifecycle, authorization class, budgets, ordered owned resources and effect ledger, transition history, cleanup, recovery, outcome, the recovery-operation journal, and any terminal-evidence binding. A monotonic sequence and predecessor identity form a compact CAS chain. Mutable recovery admits the pre-effect sequence-zero `READY` checkpoint created by `BEGIN_ATTEMPT` only when it already carries the exact five-resource activation plan; its owned resources, effect ledger, and reservation usage are still empty at that boundary. It also admits exact interrupted `QUALIFYING` and ordinary `FAILED_RECOVERABLE` heads; no other `READY` shape may spend recovery authority. A separate read-only terminal admission accepts a fully validated `QUALIFIED` head, an exact locally authorized cleanup-verified `FAILED_CLOSED` head, or a fully validated `READY/COMPLETE` recovery head. Each terminal form must carry its exact deterministic evidence identity and final lifecycle provenance. One shared semantic validator governs every already-granted mutable journal and terminal `READY/COMPLETE` admission: it requires the non-null exact anchor and grant, the fixed `VERIFY_RECOVERY_AUTHORITY` slot in `RESULT_APPLIED`, the complete exact reviewed-recovery receipt and all digest/binding/slot cross-links, fixed `16/15` reservation limits with valid non-overdrawn and non-undercounted budgets, and a legal continuous transition history whose final transition derives from that grant. After the state and chain validate, an exact authoritative-head read must prove that the loaded checkpoint is the current head. Terminal admission then returns those exact bytes without a new grant, budget spend, inspection, mutation, or transition; a rejected, unreadable, malformed, different, or nonterminal head instead follows the ordinary recovery rules or returns a minimal typed non-journal failure projection with explicit unknown checkpoint disposition and no checkpoint claim. Only for an admitted mutable prefix does the historically reviewed recovery authority receive the exact loaded checkpoint as an immutable recovery anchor and attest that anchor, envelope, ordered resource-plan digest, operation reservation, and journal identity. A rejected grant causes zero persistence, inspection, or mutation. A valid grant, its anchor, its consumed request budget, exact receipt digest, `RECOVERY_CONTROLLER` class, and review provenance transition are carried atomically into the next authenticated CAS descendant. An admitted pre-effect prefix transitions through reviewed `FAILED_RECOVERABLE`, inspects every exact fixed-plan locator, and closes durably at `READY/COMPLETE` with zero reconciliation and creation only when every locator-bound inspection proves `ABSENT`. Every later low-level call must prove, before even reading the head, exact equality among the supplied candidate/review/class, durable grant review/class, authority-receipt approval, and journal review approval.

Every non-sequence-zero recovery prefix is semantically validated before the current-head adapter or reviewed authority can run. Its history must start at `READY`, remain edge-continuous, end at the loaded lifecycle, and bind every `LOCAL_QUALIFICATION` row to the exact qualification review and every `RECOVERY_CONTROLLER` row to the durable grant review. Missing, truncated, divergent, or wrong-review history is never normalized into a new controller history. A fresh grant transitions only from the already-validated loaded lifecycle, and the complete granted candidate is revalidated after its next checkpoint identity is derived but before its CAS adapter is invoked.

Each recovery slot has one checkpoint-authenticated state: `NOT_STARTED`, `RESERVED`, `RECEIPT_KNOWN`, or `RESULT_APPLIED`. Any progressed slot requires the exact durable grant, anchor, authority-receipt digest, review digest, `RECOVERY_CONTROLLER` class, and final authorization-history entry for the current lifecycle. The authority binding derives from the immutable recovery anchor and fixed authority slot. Every non-authority binding additionally commits the exact causal prerequisite receipt: authority receipt before initial inspection, exact applied `PRESENT` inspection before deletion, and exact applied deletion before post-delete verification. Inspection fields are status- and resource-sensitive: Storage `PRESENT` requires a nonempty observed version, Storage `ABSENT` or `AMBIGUOUS` permits only an omitted or null version, and non-Storage observations cannot carry that Storage-only field. A deletion prerequisite additionally proves an existing ledger row, a reserved or applied exact qualification-create slot, the row and observation's exact creation-slot cross-link, and exact expected-version equality for Storage. Reservation is durable before inspection or cleanup mutation; an operation-specific allowlisted and status-valid receipt is durable before its result is applied; and the applied result is durable before its dependent slot starts. Malformed or nonterminal adapter output never advances to `RECEIPT_KNOWN`; the durable `RESERVED` predecessor remains retryable. A crash at any boundary reloads the actual latest head and reuses the original binding and valid receipt without consuming budget or repeating the underlying adapter call. The exported low-level controller additionally requires a capability derived from that exact current checkpoint and durable grant, and rechecks the authoritative head before any recovery slot can advance. The authority slot is the one exception to pre-call reservation: its deterministic anchor binding is presented before any persistence so rejected authority remains side-effect free, then the accepted grant and budget are persisted together. Terminal `READY` is produced only from an authorization reconstructed from the validated durable grant; the final history row must be the exact `FAILED_RECOVERABLE -> READY` controller transition carrying that grant's review digest. Recovery intentionally does not require the current repository candidate to remain byte-identical, so an authority-attested historical journal remains cleanable after later candidate drift; recovery can create no effects. It validates a one-to-one effect ledger, exact creation provenance, locator ownership, and Storage version before cleanup. It processes the ledger in dependency-safe reverse effect order, durably records each resource-local categorical failure, and continues every still-safe exact-owned resource. A Storage replacement proven by version mismatch is marked `VERSION_MISMATCH_PRESERVED`, skipped without another adapter call on retry, and cannot starve later branch, Preview, environment, row, or other exact-owned cleanup; any preserved or otherwise unresolved residue keeps the final result recovery-needed and cleanup-unverified. Missing, rejected, unsafe, or uncloneable recovery loads return the same sanitized unknown, unverified, recovery-needed non-journal projection; they never fabricate physical zero or `NOT_REQUIRED` recovery.

The recovery-operation journal also carries the complete authenticated qualification-operation journal beside its compact slot usage. Each fixed qualification request/create/delete/verifier slot is `NOT_STARTED`, durably `RESERVED`, or `RESULT_APPLIED`. A progressed slot records its zero-based ordinal, exact predecessor proof, and reservation proof derived from the fixed journal, operation reservation, ordinal, predecessor, and operation slot. The first predecessor is a domain-separated root; every later proof extends the preceding proof, forming an acyclic append-only chain that is already inside the successful pre-effect checkpoint. An applied slot contains the exact recursively safe receipt and canonical receipt digest, and the receipt must repeat its exact reservation proof and operation-specific bindings. The validator independently reconstructs the entire proof chain, requires it to be a prefix of one exact executable path, requires an applied authority before namespace and applied namespace plus prior creates before later creation, and enforces plan-order creation, staging, exact reverse deletion, and the applicable success or compensation verifier on both mutable and terminal admission. Null proof fields are valid only for `NOT_STARTED`; they never establish ordering. Budget use must equal, not merely bound, the number of recorded qualification reservations plus every progressed recovery slot, under the fixed `16/15` reservation. Qualification usage is restricted to the exact derived slots and is tied to owned-resource creation provenance and the required authority/namespace prefix. A terminal `QUALIFIED` journal must close the exact success operation set: authority, namespace, every original creation receipt, read-only staging, every non-retained deletion, and the single success verifier; the retained Preview delete and failure-only verifier remain untouched. A local terminal `FAILED_CLOSED` journal must carry the exact reviewed `QUALIFYING -> FAILED_CLOSED` transition, no recovery grant or controller progress, no retained ledger row, exact reverse cleanup receipts for every possibly applied effect, and the final locator-bound zero-resource verifier. One shared emitter-pair validator applies to mutable journals, terminal journals, recovered states, and compact evidence: `RETAINED` exists only as the exact terminal `QUALIFIED` Preview; `NOT_REQUIRED` requires `CLEANED`, a null creation receipt, a non-applied creation slot, and untouched qualification/recovery delete slots; reserved or receipt-known delete uncertainty preserves the prior `APPLIED` or genuinely unconfirmed effect status; exact deletion becomes `CLEANED/APPLIED` and exact absence verification becomes `CLEANED/VERIFIED`; a later contradictory post-delete observation returns the exact effect to `APPLIED/UNCERTAIN` (or genuinely unconfirmed `UNCERTAIN/UNCERTAIN`) and remains recovery-pending; and Storage mismatch stays `VERSION_MISMATCH_PRESERVED` under recovery-pending controls. A shared per-plan-position finite-prefix validator further couples each recovery inspection, deletion, and verifier `NOT_STARTED`/`RESERVED`/`RECEIPT_KNOWN`/`RESULT_APPLIED` phase to the exact ledger mutation applied in the same checkpoint. Missing-ledger positions can never progress deletion or verification; applied initial absence, creation-response-loss ownership proof, Storage mismatch, delete result, and post-delete verification each require their exact emitted ledger decision, and no applied slot can replay a skipped ledger callback after restart. The selected durable operation slot, not a stale `CLEANED` label, determines whether an observation is the initial recovery inspection or post-delete verification. A qualification-cleaned resource that is later observed at the exact owned locator and, for Storage, exact expected version atomically reopens to `APPLIED/UNCERTAIN` after confirmed creation or `UNCERTAIN/UNCERTAIN` after genuinely unconfirmed creation before the unused bounded recovery delete; `AMBIGUOUS` stays unresolved without deletion, `ABSENT` closes idempotently, and wrong-version Storage becomes mismatch-preserved. A qualification-origin `VERSION_MISMATCH_PRESERVED` row requires its recovery inspect/delete/verifier slots to remain untouched, while a recovery-origin mismatch requires the exact applied initial inspection that emitted it. The structural evidence schema enforces the same status/cleanup pairs and null receipt for `NOT_REQUIRED`; cross-slot receipt and chronology bindings remain mandatory in the semantic validator. Verifier meaning is status-sensitive on every mutable and terminal admission: a retained-Preview delete before slot 3 permits only the exact zero-resource meaning, while a later delete never changes an already applied one-retained success receipt. Verifier or delete adapter faults may leave their stable slots `RESERVED`; those exact crash prefixes remain admissible only with their causal order and unresolved ledger/control state. If a delete effect succeeds but its response is lost, a later exact zero verifier proves physical absence but does not invent the missing deletion receipt: the journal stays `FAILED_RECOVERABLE`, cleanup-unverified, and recovery-pending. Likewise, an exact Storage `VERSION_MISMATCH` receipt remains paired with `VERSION_MISMATCH_PRESERVED`; even if the replacement later disappears and slot 3 physically verifies zero, the result remains recovery-pending rather than claiming completed cleanup. Slot 4 can prove zero only after the applied success receipt and the progressed retained-Preview delete. Thus a slot-3 zero rewrite, retained-success rewrite after an earlier delete, missing completed slot 4, or reversed verifier/delete order cannot turn compensation into an ordinary failure closure. A rejected or malformed primary success verifier deletes the provisional Preview but remains `FAILED_RECOVERABLE`, unverified, and recovery-needed rather than manufacturing a second completed verifier story. A terminal `READY/COMPLETE` journal additionally closes every ledger row against the exact recovery operation path: locator-bound initial absence with untouched delete/verifier slots, or exact initial presence, exact key/locator/CAS deletion receipt, and exact post-delete absence receipt. Runtime and terminal recovery use one status-sensitive inspection receipt validator: an `ABSENT` missing-ledger observation cannot carry a creation slot, and a ledger-backed observation may carry only the exact creation slot. Malformed inspection output is rejected before `RECEIPT_KNOWN`, leaving the durable `RESERVED` predecessor retryable; every derived recovery terminal is semantically validated after its checkpoint identity is constructed and before the checkpoint adapter. Recovery walks the complete fixed ordered resource plan in reverse even when an authenticated mutable prefix has no owned/ledger row for a plan member: exact `ABSENT` may close that plan position, while `PRESENT` is ownership-unproven and `AMBIGUOUS` is unresolved, with no reconciliation call. Missing, substituted, contradictory, or extra operation proof cannot support `QUALIFIED`, `VERIFIED`, or `NOT_REQUIRED` cleanup.

`UNCERTAIN` is never a deletion-free label: it requires an exact qualification or recovery delete slot already `RESERVED`/`RECEIPT_KNOWN`, or an exact applied deletion followed by a causally later contradictory verification. When authoritative readback proves a delete reservation did not commit, the bridge restores the pre-reservation cleanup label before any later checkpoint. Recovery admission validates each inspection, deletion, and post-delete receipt with the same operation-specific allowlist used at acquisition, and recomputes each non-authority binding from its exact predecessor receipt; co-present but reordered inspection, deletion, and absence claims cannot close cleanup.

## Fresh ownership and adapters

Each planned resource has one exact owner and one compact ledger row. Its owner binds candidate identity, unique run ID, phase, operation class, resource type, full canonical locator digest, and cleanup policy; its resource key contains that full locator digest. The authenticated namespace receives the exact ordered plan and must return an exact locator-bound `ABSENT` proof for every entry before the first creation intent. The row separately tracks creation and cleanup, the exact creation operation slot, and the canonical digest of a verified `CREATED_NEW` receipt with the same resource key, locator digest, authority-envelope identity, reservation proof, and slot identity. The controller durably appends the owned resource and its creation `INTENT_ONLY` row before it reserves the create slot or invokes the creation adapter; it then durably records the exact creation receipt and `APPLIED`, or records `UNCERTAIN` on a rejected/unconfirmed result. That ordering makes a true pre-create prefix distinguishable from a later applied effect whose owned/ledger suffix was erased. Before every cleanup mutation it attempts to checkpoint cleanup `INTENT_ONLY`; immediately after the adapter it attempts to checkpoint `APPLIED`, `UNCERTAIN`, or `VERSION_MISMATCH_PRESERVED`, and locator-bound physical absence proof advances successful cleanup to `VERIFIED`. During failure cleanup only, `CHECKPOINT_STATE_UNKNOWN` is accumulated as `CLEANUP_CHECKPOINT_STATE_UNKNOWN` but cannot escape the reverse loop, suppress the single stable-slot exact cleanup of an earlier phase-owned effect, skip the bounded final verifier, or bypass deterministic evidence generation. Exact ownership and full locator identity are proved before each call, Storage deletion retains its exact expected-version CAS contract, and `INTENT_ONLY`, substituted, ambiguous, unowned, or version-mismatched targets receive no broadened deletion authority. Because the durable head remains unknowable, even physically successful cleanup returns a strict recovery-needed non-journal projection rather than a full mutated state or a verified-zero claim. Qualification attempts a final durable `QUALIFIED`, `FAILED_RECOVERABLE`, or `FAILED_CLOSED` checkpoint with the finalized evidence identity, and recovery attempts a durable `READY` checkpoint with `COMPLETE`. Before every write, including an interrupted-finalization checkpoint, the bridge validates the same complete lifecycle/history/operation semantics used on later admission; an interrupted candidate always has an exact `QUALIFYING` history tail. A full journal is returned only after the exact final bytes receive an authenticated checkpoint receipt or exact readback. Persistent or unreadable finalization instead returns a strict `QUALIFICATION_FAILURE_PROJECTION` with no checkpoint, journal, ledger, resources, or budgets, alongside deterministic sanitized evidence; the separately captured latest authenticated head remains the only recovery input. Recovery uses the same per-effect checkpoint contract and exact receipts to resolve a create-result crash window or an already-completed cleanup without repeating an external mutation. Discovery patterns are not accepted as locators or mutation authority; ambiguous, duplicate, unbound, pre-existing, or substituted plans fail before effects.

The minimal adapter boundary covers one temporary branch, one nonproduction Preview, one Preview environment/access record, one read-only staging verification, one synthetic database fixture, one synthetic Storage object, exact-version Storage CAS cleanup, and final cleanup verification. Each environment binding is an ordered exact key-to-ID map, not a positional ID list: partial creation and deletion checkpoints preserve which allowlisted key owns each surviving ID, a 404/200 exact pair remains safely inspectable as `PRESENT`, and retry cleanup skips only the exact absent member while deleting the exact surviving member. Environment resolution refreshes even a stale in-memory partial map from the authoritative branch-scoped inventory; recovery persists that validated rediscovery before its one-use inspection receipt can enable cleanup, and final physical-zero verification always inventories the full exact environment namespace instead of trusting only remembered IDs. Every successful Vercel Preview or environment list must carry its required array and a non-array pagination object with an exact nonnegative bounded `count` equal to the array length and an explicit terminal `next: null`; every returned member is structurally validated before ownership filtering. A missing, contradictory, element-malformed, wrong-typed, oversized, or nonterminal collection is ambiguous and can prove neither freshness nor physical zero. A second-create response loss therefore remains detectable, and a later delete-response loss retains the exact ID needed for retry. Preview creation, readback, rediscovery, cleanup, and final verification share one exact identity predicate over deployment ID, normalized nonproduction `.vercel.app` hostname, run/candidate metadata, project/team, Git repository/ref/SHA, target, and recognized lifecycle. Staging performs no application probe until a bounded eight-read sequence observes that same exact deployment at `READY`; terminal failure, identity drift, untrusted hostname, pagination, ambiguity, or timeout fails closed. Before the first request or effect, the durable checkpoint adapter must atomically create the journal with `BEGIN_ATTEMPT`; its exact categorical `ATTEMPT_ALREADY_EXISTS` rejection is preserved before readback, so an identical pre-existing sequence-zero head cannot be adopted by a second caller.
